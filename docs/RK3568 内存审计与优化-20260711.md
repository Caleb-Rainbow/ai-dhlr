# RK3568 内存审计与优化（2026-07-11）

> 针对运行 `ai-dhlr`（动火离人安全监测系统）的 RK3568 边缘设备（1.9GB RAM）做的一次完整内存/磁盘审计与优化。
> 配套通用指南见 [RK3568 边缘设备部署与内存优化指南.md](./RK3568%20边缘设备部署与内存优化指南.md)。本文记录**本次具体诊断结论、代码改动与设备运维步骤**，便于在其它同型号设备上复现。

## 1. 结论

- **不会因"缓慢泄漏"撑爆内存**：主进程稳态 RSS ~775MB 是平台期（实测 45 秒内 3 次采样完全一致、18 小时峰值 VmHWM 仅 836MB），热路径上所有内存集合均有上界。
- **真正风险是余量薄 + 零 swap 的尖峰 OOM**：1.9GB 内存被桌面 GUI（~600MB）+ 主进程（~775MB）+ 桌面全家桶占满，可用内存仅剩 684MB、free 仅 28MB，**且无 swap**。任何分配尖峰（大告警图 base64、RTSP 帧、RKNN 内部缓冲）都可能触发 OOM Kill。
- **附带发现一个磁盘累积根因 bug**：日志按天保留（retention）形同虚设，实测堆积 391MB（跨 6 个月）。快照无任何保留策略，堆积 41MB（466 个文件）。

本次优化把**可用内存从 684MB 提升到 1.4GB（另加 1GB swap 兜底）**，并修复磁盘只增不减的问题。

## 2. 问题诊断（实测数据）

设备：`linaro@192.168.2.170`，已运行 18h20m。

### 2.1 内存画像

| 进程 | RSS | 说明 |
|---|---|---|
| `src/main.py`（主推理服务） | **775 MB** | 稳态；峰值 VmHWM 836MB；RssAnon 676MB（堆），VmData 963MB（~290MB 已释放未归还 OS，Python arena 碎片，非泄漏） |
| `src.ble`（蓝牙配网服务） | 38 MB | 健康 |
| Xorg + xfce4 全家桶 | **~600 MB** | 桌面环境，对无头设备纯浪费 |

系统：total 1.9GB / used 1.2GB / free **28MB** / available 684MB / **swap 0B**。

### 2.2 磁盘累积

- `logs/`：**391MB**，最早文件 2026-01（6 个月前），个别单日达 28MB。`retention_days=7` 本应只保留 7 天。
- `snapshots/`：**41MB / 466 个 `.jpg`**，跨 1 月至今，**完全无清理**。
- `cache/offline_records.json`：2 字节（`[]`），正常。

### 2.3 日志保留失效根因

`src/utils/logger.py` 的 `DailyFileHandler._cleanup_old_logs()` 原实现：

```python
# 旧（错误）
date_str = f.stem.split("_", 1)[-1]   # "fire_safety_2026-01-13" → "safety_2026-01-13"
file_date = datetime.date.fromisoformat(date_str)  # ValueError → 被 except 吞掉
```

日志文件名格式是 `{prefix}_{YYYY-MM-DD}.log`，而 `prefix = "fire_safety"` **本身含下划线**。`split("_", 1)` 在第一个下划线处断开，得到 `safety_2026-01-13`，`fromisoformat` 永远抛 `ValueError`，被 `except (ValueError, IndexError): pass` 静默吞掉 —— **没有任何日志被删除过**。

## 3. 代码改动（commit `9bd9a44`）

| 文件 | 改动 | 原因 |
|---|---|---|
| `src/utils/logger.py` | ① 修日期提取：按已知 prefix 长度截取 `f.stem[len(prefix)+1:]`；② 新增告警快照 mtime 清理（默认 3 天，启动清一次 + `save_snapshot` 节流每小时一次） | 修复日志保留根因 + 补快照保留缺口 |
| `src/utils/config.py` | `LoggingConfig` 加 `log_retention_days=7`、`snapshot_retention_days=3`，接入解析与序列化 | 让保留天数可经 `config.yaml` 配置 |
| `src/patrol/patrol_manager.py` | `PatrolState.results` 由无界 `List` 改 `deque(maxlen=200)`；`to_dict` 改 `list(self.results)[-20:]`；`start_patrol` 改 `.clear()` | 唯一一个无界内存列表，长期运行下缓慢吃内存 |
| `src/camera/frame_cache.py` | `get_or_encode` 入口加 60s 时间门调 `cleanup_expired()` | 回收已弃用的 quality/摄像头组合残留帧（无额外线程） |
| `src/main.py` | `event_logger.setup(...)` 透传 `log_retention_days` / `snapshot_retention_days` | 把配置接到 logger |

全量 **142 单测通过**（`./gradlew` 不适用，本项目用 `pytest`：`python -m pytest -q`）。

### 配置项（可选，写进 `config.yaml`）

```yaml
logging:
  level: INFO
  log_dir: logs
  snapshot_dir: snapshots
  log_retention_days: 7        # 日志保留天数，0=永不清理
  snapshot_retention_days: 3   # 告警快照保留天数，0=永不清理
```

## 4. 设备运维步骤

> 设备：`linaro@192.168.2.170`（密码 `linaro`，linaro 用户可 `sudo`）。同型号设备照搬即可。
> 三步相互独立，可单独执行。**顺序建议：加 swap → 部署代码 → 关 GUI**。

### 4.1 加 1GB swap（OOM 兜底）

eMMC 写寿命有限，故 `swappiness=10`（极度偏向 RAM，仅在 OOM 临界才用 swap）。

```bash
sudo fallocate -l 1G /swapfile || sudo dd if=/dev/zero of=/swapfile bs=1M count=1024
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
# 开机自动挂载
grep -q swapfile /etc/fstab || echo "/swapfile none swap sw 0 0" | sudo tee -a /etc/fstab
# 偏向 RAM
sudo sysctl vm.swappiness=10
grep -q swappiness /etc/sysctl.conf || echo "vm.swappiness=10" | sudo tee -a /etc/sysctl.conf
free -h   # 确认 交换 一行出现 1.0Gi
```

### 4.2 部署代码改动

代码已合并到 `origin/main`（commit `9bd9a44`）。设备常规更新方式：

```bash
cd ~/ai-dhlr
git fetch origin
git pull origin main          # 若有未提交改动见 §6
sudo systemctl restart ai-dhlr
sudo systemctl is-active ai-dhlr   # 应为 active
```

> 若设备无网络/不走 git，可从开发机直接 scp 五个文件后重启：
> `scp src/utils/{config,logger}.py src/patrol/patrol_manager.py src/camera/frame_cache.py src/main.py linaro@<ip>:~/ai-dhlr/src/...`（注意各自子目录）。

重启后启动日志会自动清理过期日志与快照，观察 journalctl：

```bash
sudo journalctl -u ai-dhlr -n 20 --no-pager
# 应看到 "日志系统初始化完成" 及（若有旧文件时）"清理过期告警快照 N 个"
```

### 4.3 关闭桌面 GUI（释放 ~600MB）

设备是无头设备（BLE + WebSocket API + RKNN 推理），桌面环境纯浪费。两个服务 `ai-dhlr` / `ai-dhlr-ble` 的 `WantedBy=multi-user.target`，关 GUI **不影响开机自启**，SSH（sshd 独立）也不受影响。

```bash
sudo systemctl set-default multi-user.target   # 开机不进图形
sudo systemctl stop lightdm                     # 立即停掉桌面，释放内存
systemctl get-default                           # 应为 multi-user.target
free -h                                          # available 应跳升 ~500-600MB
```

## 5. 验证结果（before / after）

| 指标 | 改前 | 改后 |
|---|---|---|
| 可用内存（available） | 684 MB | **1.4 GB** |
| swap | 0 B | **1.0 GB**（swappiness=10） |
| `logs/` 占用 | 391 MB（跨 6 月） | **1.0 MB**（仅近 7 天） |
| `snapshots/` 占用 | 41 MB（466 个） | **40 KB**（仅近 3 天） |
| OOM 风险 | 尖峰即崩 | 余量充足 + swap 兜底 |

清理即时回收磁盘约 **432MB**（391M 日志 + 41M 快照）。

## 6. 回滚

```bash
# 恢复 GUI
sudo systemctl set-default graphical.target && sudo systemctl start lightdm

# 删除 swap
sudo swapoff /swapfile && sudo rm /swapfile
sudo sed -i '/swapfile/d' /etc/fstab

# 回退代码（若曾 scp 部署，设备上留有 .bak_memfix 备份）
cd ~/ai-dhlr
for f in src/utils/config.py src/utils/logger.py src/patrol/patrol_manager.py src/camera/frame_cache.py src/main.py; do
  [ -f "$f.bak_memfix" ] && mv "$f.bak_memfix" "$f"
done
sudo systemctl restart ai-dhlr
# 若走 git，回退到本次提交前：git reset --hard b4d6692
```

> 部署时为稳妥在每个改动文件旁留了 `*.bak_memfix` 备份；确认生产稳定后可删除：`rm ~/ai-dhlr/src/**/*.bak_memfix`。

## 7. 后续注意

- **主进程内存仍是 ~775MB 量级**：这是 YOLO11m RKNN 推理 + 双摄像头 + OpenCV/numpy 的固有占用，不是泄漏。若要进一步压，方向是换更小的模型（如 yolov11n-sim.rknn，仓库已附）或减少摄像头分辨率。
- **桌面 GUI 已关**：如需临时恢复（本地调试、看 web UI），按 §6 执行 `start lightdm`；用完再停。
- **设备 git 状态**：本次部署时设备 `~/ai-dhlr` 存在与本优化**无关的未提交改动**（`src/ble/service.py`、`tests/test_ble_service.py`），且 HEAD 落后 `origin/main` 两个提交，导致 `git pull` 被拒。这部分需人工 reconcile（决定那份 ble 改动是丢弃还是保留后合并），不属于本次内存优化范围。reconcile 完成后正常 `git pull` 即可让设备 git 与远端一致。
